# verme-gate (ex dsh-mcp-access)

Плагин DSH: токен доступа = ключ LiteLLM виртуального ключа, MCP-серверы подключаются
только за шлюзом LiteLLM (никаких локальных stdio-серверов), каталог моделей агента = права ключа.
Видимое имя (cordis name, слот настроек, страница) — `verme-gate`; каталог и credential-ref'ы
(`MCP_ACCESS_*`) сохранены ради совместимости состояния.
Две половины: host (`index.js`) и нативный экран в клиенте DSH (`lib/client.js`).

- точка входа: `index.js` (ESM)
- клиентская половина: исходник `client/index.cjs`, сборка `node scripts/build-client.mjs` → `lib/client.js`
- экран: Settings → «verme-gate» (слот `settings.section`, id `verme-gate`)
- автономная страница: <pagePath> (по умолчанию `/verme-gate`), API: `<pagePath>/api/{state,diag,refresh,secret,active,token-key,verify}`
- самотест: `node selftest.mjs` (статические и контрактные проверки, без сети)
- установка как бандл: `package.json` объявляет `dsh.bundle.patch` → `cordis.patch.yml`

## Бандл-патч (что установка добавляет в профиль)

`cordis.patch.yml` — топ-уровневый массив patch-записей; ряд плагина объявляется через `insert`
(слой бандла — это patch-слой поверх собранного дерева), `name` относительный (`./index.js`),
потому что bare-имя пакета из контекста лоадера не резолвится.

Кроме строки плагина патч объявляет только `agent-default-model` (`provider: dshlab`, модель
`deepseek/deepseek-v4-pro`). **Каталог моделей в патче больше не объявляется** — маршрутом
владеет плагин, см. следующий раздел.

## Маршрут моделей: свой провайдер в плагине

Плагин **владеет маршрутом llm сам** — по образцу `dsh-grok-subscription` и `dsh-codex-connect`:
`@earendil-works/pi-ai` `createProvider({getModels})` + `PiAiAdapter` из
`@deepseek-ai/dsh-llm-pi-ai` + `ctx.llm.registerAdapter([llmProvider], adapter)`
(`lib/gateway-route.js`, вызов — `index.js`, `installGatewayRoute`).

Почему так, а не каталогом в конфиге: селектор DSH читает модели только у провайдера
(llm-pi-ai отдаёт объявленное в `cordis.patch.yml`), а регистрировать модели в рантайме
llm-pi-ai не умеет. Свой маршрут закрывает это: `getModels()` читает **текущий** каталог прав
активного ключа, поэтому

* в селекторе ровно модели, доступные ключу активного токена (62 у полного ключа ai-labs на
  2026-10-27; число живое — шлюз добавляет модели сам, плагин их видит сразу);
* смена токена меняет список без пересборки бандла и без рестарта;
* ёмкости берутся из `GET /v1/models` (`max_input_tokens` / `max_output_tokens`), дефолт —
  131072/32768: у `deepseek/deepseek-v4-pro` это 1000000/393216, и автокомпакт считается от них.
  Поля шлюз отдаёт не для всех моделей (6 из 62) — остальным остаются дефолты;
* состояние маршрута видно в `/verme-gate/api/state` → `models.route` и `models.limits`.

Стриминг, ретраи (политика `resolveRetryPolicy`: 5 попыток, только RATE_LIMIT/SERVER/TIMEOUT/
TRANSPORT/EMPTY_RESPONSE), отмена по `AbortSignal` и нормализация картинок — pi-ai и
`PiAiAdapter`, плагин их не дублирует. Ключ на каждый вызов отдаёт `resolveApiKey` из
credential-store (ref = `llmSecretRef`), пустой ключ — `MISSING_CREDENTIAL`.

### Когда каталог перечитывается

`getModels()` отдаёт то, что плагин узнал последним, поэтому важно, **когда** он спрашивает шлюз:

| событие | что делает |
|---|---|
| старт плагина | `GET {llmBaseUrl}/models` активным ключом (первый каталог) |
| смена активного токена, запись ключа, подключение токена, `POST /api/active` | перечитывание сразу |
| кнопка «Обновить» на экране (`POST /api/refresh`) | перечитывание по требованию |
| авто-ретрай после отказа (`R3`) | перечитывание с нарастающей паузой |
| таймер `modelRefreshMs` (по умолчанию 300000 = 5 мин) | перечитывание каталога; `0` — выключить |

Зачем таймер: права ключа меняются **на шлюзе**, без нашего участия (админ отозвал модели) —
без него селектор держал бы старый набор до следующего события. Проверено: отзыв 62 → 4 модели
подхватился автоматически на ближайшем тике, без рестарта и без перезагрузки страницы.

Авто-таймер идёт **лёгким путём** (`refreshModelCatalog`): ключ → свой ref, каталог → `/v1/models`,
дефолтная модель. Барьер не поднимается, MCP-серверы не перемонтируются, адаптеры не
перетряхиваются — обновление каталога не может дёрнуть работающие инструменты. Тик планируется
цепочкой `setTimeout` **после** завершения предыдущего, поэтому интервал равен объявленному
(прежняя реализация глушила тик проверкой «каталог уже обновлён?» и растягивала 5 минут в 10).

Кнопка «Обновить» остаётся тяжёлой: это жест «почини всё», он перечитывает и монтирования.

### Ёмкости и автокомпакт (почему «объявил 256k, а компакт на 100k»)

DSH считает порог автокомпакта так (`dsh-compaction-basic/lib/index.js:132`):

```
порог = min(ratio × окно, окно − объявленный вывод − headroom),  ratio = 0.8, headroom = 65536
```

Отсюда три следствия, которые дороже всего стоят:

* **Headroom съедает 64k у каждой модели.** Окно 131072 даёт порог **65536** (половина окна), окно
  262144 — **196608**, окно 360448 — **294912**. Headroom задаётся в пресете агента
  (`compaction-basic.headroomTokens`), из patch-слоя профиля его не поменять: запись в пресете
  вложена в список плагинов пресета, а patch адресует только верхний уровень и группы.
* **Объявленный вывод вычитается целиком.** Шлюз отдаёт вывод размером с четверть окна
  (`anthropic/claude-opus-5.5`: 200000/64000) — и порог падает до 69k. Поэтому плагин режет
  объявленный вывод потолком `maxOutputTokensCap` (по умолчанию 32768).
* **Окно надо объявлять с запасом**: `объявленное окно = целевой порог + объявленный вывод + headroom`.
  Объявить больше физического нельзя — шлюз ответит ошибкой на переполнении.

Отсюда рабочая настройка «компакт на X, когда шлюз молчит» — одно число
`defaultContextWindow`, потому что при нулевом резерве вывода оба слагаемых совпадают:

| `defaultContextWindow` | порог автокомпакта |
|---|---|
| 131072 (умолчание) | 65536 |
| 196608 | 131072 |
| 262144 | 196608 |
| **327680** | **262144** (0.8·327680 = 327680 − 65536) |
| 393216 | 314572 |

Формула подбора: `порог = 0.8 · defaultContextWindow` (пока `0.2·окно ≥ headroom`) —
отсюда 327680 для 256k. Если агент объявляет `maxTokens` уровнем выше (резерв вывода больше нуля),
из окна вычитается ещё и он: `порог = окно − вывод − headroom`. Умолчание применяется **только** к
моделям, про которые шлюз молчит; у остальных окно берётся из шлюза или из `modelLimits`.

Ёмкости шлюз отдаёт не для всех моделей, поэтому есть два источника и ручное перекрытие:

1. `GET {llmBaseUrl}/models` — `max_input_tokens`/`max_output_tokens`;
2. `GET {llmBaseUrl}/model/info` — `litellm_params.max_input_tokens/max_output_tokens` (там они есть
   у части моделей, которых нет в первом источнике);
3. `modelLimits` в конфиге (`id → {contextWindow, maxTokens}`) — перекрывает оба.

Что получится на практике, видно в `/verme-gate/api/state` → `models.compaction.effective`
(окно, вывод и предсказанный порог по каждой модели). Поля
`compactionHeadroomTokens`/`compactionThresholdRatio` нужны только для этого расчёта — поставь их
равными настройке своего пресета, иначе цифры будут врать.

Две особенности, которые проще знать, чем ловить:

* **«Off» — это не выключение.** Шлюз не принимает «не думать», поэтому `thinkingLevelMap.off`
  отправляет минимальный уровень (`reasoning_effort: low`); `off: null` в pi-ai даёт
  `UNSUPPORTED_REASONING_EFFORT`, то есть падение хода. Проверено на 4 семействах моделей.
* **Выбор модели сам чинится при смене токена.** Если в сессии стояла модель, которой у нового
  ключа нет, `ensureDefaultModel` + `reselectLiveAgents` переезжают на первую разрешённую
  (в открытой странице кнопка модели меняется без перезагрузки), и ход проходит. Обратно
  прежний выбор не возвращается — переезд односторонний.

**Провайдер с id `llmProvider` нельзя объявлять в патче профиля** — два владельца маршрута
конфликтуют; `cordis.patch.yml` бандла его больше не содержит. Если объявление есть, плагин
пишет в журнал ошибку и не регистрируется (работает откат: каталог из патча, сужённый
`installModelGate()`).

Краевые случаи (повторные вызовы, отмена, сеть, 401/403/429, пустой каталог, смена токена,
конфликт маршрута, двойной рестарт) — чек-лист с контрактом и командами проверки:
[docs/llm-route-edge-cases.md](docs/llm-route-edge-cases.md).

### Уровень размышлений маршрута (`defaultReasoningEffort`)

Профиль маршрута объявляет уровень, который DSH берёт, когда агент/сессия свой не передал:
`dsh-llm-pi-ai` делает `options.reasoningEffort ?? profile.reasoning`
(`lib/index.js:1953`, значение по умолчанию для модели — `modelInfo`, там же `1914`). До 0.3.6
профиль был жёстко `'low'`, поэтому при пустом `agent-default-model.reasoningEffort` **все**
сессии разговаривали на низком уровне.

Теперь это `defaultReasoningEffort` (по умолчанию `medium`, значения — уровни DSH
`off|minimal|low|medium|high|xhigh|max`). Приоритет: явный выбор агента → значение из плагина.
`off` на этом шлюзе — минимальный уровень, а не отключение (карта `THINKING_LEVEL_MAP`).

Проверено в лабе: с пустым `reasoningEffort` у `agent-default-model` чип селектора показывает
**Medium**; при `reasoningEffort: high` — **High** (выбор агента выигрывает).

### Когда выбранной модели больше нет в правах ключа

Ключ — это профиль, поэтому каталог может сузиться под уже выбранной моделью (админ отозвал
модель, сменился токен). Плагин подставляет первую доступную модель, но по умолчанию **не**
трогает чужое:

| поле | по умолчанию | что делает |
|---|---|---|
| `persistDefaultModelSwap` | `false` | `true` — переписать сохранённый выбор DSH (`saveSelection`); `false` — подмена только в памяти |
| `reselectAgentsOnModelLoss` | `false` | `true` — переставить модель живым агентам; `false` — подмена действует только для новых сессий |

Событие всегда видно: строка `WARN default model unavailable (…) -> substituted …` в журнале и
`models.defaultSwap` (`{ at, from, to, persisted, reassignedAgents }`) в `GET /api/state`.

### `installModelGate()` — что осталось

Обёртка `llm.listModels`, которая оставляет только id из прав ключа. При живом маршруте она
избыточна (маршрут отдаёт тот же набор), но остаётся страховкой на откат: если маршрут не
поднялся (`llmProvider` пуст, конфликт, нет `ctx.llm.registerAdapter`), селектор показывает
каталог из патча, сужённый правами ключа. В v2 — убрать.

## Конфиг

| поле | смысл |
|---|---|

| `stateFile` | абсолютный путь активного токена; обязан лежать внутри `DSH_HOME` (по умолчанию `$DSH_HOME/storages/dsh-mcp-access.json`) |
| `logFile` | абсолютный путь журнала; может быть вне `DSH_HOME` (только предупреждение в состоянии) |
| `journalMaxBytes` | ротация журнала (по умолчанию 1 МиБ, файл `<logFile>.1`) |
| `gatewayBaseUrl` | база шлюза для `GET /v1/mcp/server`, `/v1/mcp/user-env-vars/status`, `/v1/models` |
| `llmProvider` / `llmSecretRef` / `llmBaseUrl` | куда писать ключ активного токена, чтобы маршрут llm-pi-ai жил правами того же ключа; дефолты: провайдер `dshlab`, ref `MCP_ACCESS_LLM_KEY`, `https://ai-labs-litellm.verme.ru/v1` |
| `modelDiscoveryTimeoutMs` | таймаут одного запроса к шлюзу (по умолчанию 20 с) |
| `modelRefreshMs` | период авто-обновления каталога (по умолчанию 300000 = 5 мин, минимум 30000, `0` — выключить) |
| `defaultReasoningEffort` | уровень размышлений маршрута, когда агент свой не задал (по умолчанию `medium`) |
| `persistDefaultModelSwap` / `reselectAgentsOnModelLoss` | писать ли конфиг и переставлять ли живых агентов при потере выбранной модели (по умолчанию оба `false`) |
| `promptsDir` | каталог своих промптов для раздела «Промпты»; пусто — встроенный набор пакета (`prompts/`) |
| `servers[]` | `name` (alias), `serverName` (^[A-Za-z0-9_-]{1,32}$), `tokenHeader`/`tokenRef` (header-режим), `tokenRequired`, `verifyTool`, `toolAllow` |
| `verifyTimeoutMs` | таймаут одной проверки `verifyTool` (по умолчанию 10 с): недоступный MCP даёт `token-unknown`, инстанс жив |
| `verifyTtlMs` | кеш результата проверки, пока значение токена не изменилось (по умолчанию 5 мин) |
| `tokens[]` | `id`, `keyRef` (credential-ref ключа LiteLLM), `servers[]` (сервер + список тулзов) |

## Нативный экран в DSH

Экран — это клиентский плагин DSH: пакет объявляет `dsh.client` в `package.json` и экспорт
`./client`, host отдаёт собранный бандл через `/plugins`. Регистрация — в слот `settings.section`
(как у сторонних плагинов, например Grok Subscription): пункт «verme-gate» в левом меню Settings,
страница не открывается отдельной вкладкой и не дублирует сайдбар.

Данные экран берёт из тех же ручек плагина на том же origin (`fetch(<pagePath>/api/…)`), периметр
проверяет host (`connection.requestRejection`). Ничего не кэшируется в localStorage, сохранённые
секреты не запрашиваются и не отображаются — `/api/state` отдаёт только факт наличия и вердикт проверки.

Что экран делает намеренно:

| правило | зачем |
|---|---|
| выбор токена в списке ≠ активация: «Применить токен» с подтверждением, после — честная фаза (`starting`/`degraded`) | случайный клик не меняет доступ всех агентов |
| нет периодического опроса: «Обновить» = чтение статусов, «Подключить заново» = `POST /api/refresh` | версия страницы на `setInterval` затирала введённый текст |
| пустое поле не сохраняется; удаление ключа — отдельное действие с подтверждением | пустой Save раньше стирал рабочий ключ |
| показываются только полученные инструменты, каждый с пометкой «Доступен» / «Ограничен в DSH» | шлюз не раскрывает запрещённые инструменты — их нельзя выдумывать; локальный `toolAllow` — ограничение вызова, а не отказ шлюза |
| `models.allowed = null` — «список не получен», а не «0 моделей» | неизвестность не выдаётся за пустое множество |
| SSO — честная заглушка: диалог объясняет, что вход не выполняется, и предлагает токен LiteLLM | сценарий SSO отложен, но место в модели данных уже есть (`group`/`source`) |

### Подключение: один ключ или SSO

Доступ на экземпляр один. Экран не переключает профили и токены: он показывает либо **«Не подключено»** с двумя
кнопками, либо одно подключение — метку, «серверов подключено: N · моделей: M», «Заменить ключ» и «Отключить».

1. «Подключить по ключу» → вставить ключ → `POST /api/key-probe` спрашивает шлюз этим ключом и **ничего не сохраняет**;
   экран показывает счётчики — «Серверы: N» (до 8 имён) и «Модели: M» — и предлагает название
   (`Ключ …<хвост>`, можно переписать). Перечня моделей в диалоге нет: длинный каталог растягивал окно на пол экрана,
   полный список живёт на вкладке «Серверы и инструменты»;
2. «Подключить» → `POST /api/token-connect`: токен появляется в `stateFile`, ключ пишется в его собственный ref, токен
   становится активным, монтирование запускается сразу. Повторное подключение **того же** ключа переиспользует
   существующий токен, а не создаёт второй;
3. «Заменить ключ» пишет новый ключ в ref активного токена (`POST /api/token-key`) и переприменяет права;
4. «Отключить» → `POST /api/disconnect`: `activeToken` становится пустым, серверы снимаются, ref провайдера
   освобождается — **ключ при этом остаётся** на этом DSH, поэтому доступ возвращается тем же ключом;
5. «Войти через SSO» — честная заглушка: провайдера входа нет, кнопка ничего не выдаёт и никуда не ведёт.

| действие | где | что происходит |
|---|---|---|
| «Подключить по ключу» | Доступ | ключ → проверка шлюзом → токен + ключ + активация; ключ не журналируется (только счётчики) |
| «Заменить ключ» | Доступ | новый ключ в ref активного токена, права пересчитываются |
| «Отключить» | Доступ | снять доступ, ключ сохранить |
| «Удалить токен и ключ» | Дополнительно | токен уходит из `stateFile` вместе со своим ключом — вернуть можно только новым подключением |
| «Скрыть токен» (из конфига) | Доступ, нижняя строка | id в `hiddenTokens[]`: экран и гранты его не видят, запись в конфиге остаётся; «Вернуть» возвращает |

Активный токен не удаляется, пока есть другой видимый (409); удаление последнего разрешено и означает «доступа нет».

### Серверы и инструменты — отдельная вкладка

`Доступ` отвечает только за подключение. Список серверов и инструментов живёт на вкладке **«Серверы и инструменты»**
и **до подключения пуст**: пока ключа нет, шлюз не сообщает, что и какие инструменты выданы, — показывать нечего
(пустое состояние с кнопкой «Перейти к подключению»). После подключения там же: сервер по строке (состояние,
«инструменты N из M», раскрытие списка) и карточка моделей: до 6 моделей видно сразу, длиннее — свёрнуто
в «Показать все N моделей» с прокруткой.

**Источник списка — шлюз, а не конфиг плагина.** Строки берутся из реестра `GET /v1/mcp/server` под ключом активного
токена: что ключу не выдано, того в списке нет вовсе (не «серых» строк, не заглушек). Подписи и описания серверов тоже
приходят из реестра. Конфиг `servers[]` может **сузить** набор и задать своё имя/подпись, но не добавить сервер:
объявленное в конфиге без гранта перечисляется отдельной сноской внизу вкладки («объявлены, но шлюз не выдаёт»).

**Требования сервера тоже генерируются, а не задаются конфигом.** Их объявляет сам MCP: шлюз отдаёт необходимые
пер-юзерные переменные через `GET /v1/mcp/user-env-vars/status` (имя, описание, признак «заполнено») плюс поля записи
сервера (`auth_type`, `is_byok`/`byok_description`, `has_user_credential`). В строке это выглядит как метка-чип
`REDMINE_PERSONAL_KEY` (подсказка при наведении — описание от сервера) и кнопка **«Переменные»**: поле ввода прямо в
строке сервера, значение уходит в шлюз ключом активного токена (`POST /v1/mcp/server/<id>/user-env-vars`, снятие —
`DELETE`), плагин его не хранит и на экран не возвращает. Логин в админку LiteLLM для этого не нужен: ручка закрыта
ключом пользователя, а не ролью админа; шлюз принимает только имена, объявленные в `env_vars` сервера. Плагин своих
полей под личные ключи серверов не держит: тот же сервер под другим ключом потребует ровно то, что объявит шлюз.

Признаки в строке сервера: `Токен не выбран` (`no-active-token`) — активного токена нет вовсе; `Нужны переменные
окружения` (`no-env`) — сервер сам требует пер-юзерные параметры, их вводят в строке этого сервера (значение уходит
в шлюз, см. ниже). Записи прошлых
применений не переживают новое применение: статусы пересчитываются с нуля.

**Заголовки, если сервис требует идентичность клиента.** Часть MCP принимает не переменную шлюза, а HTTP-заголовок
(`extra_headers` в объявлении сервера). Для такого сервера в строке появляются «требует: заголовок X-…» и кнопка
**«Заголовки»**: имя приходит из объявления (реестр, иначе — из описания сервера), значение вводит человек, хранится оно
только в credential-store (`MCP_ACCESS_SRV_<NAME>_HEADERS`, JSON) и на экран не возвращается («задан/не задан»). Пока
значения нет, сервер **не монтируется** — статус `no-header` («Нужны заголовки»): лучше не дать агенту инструменты,
чем звать сервис без идентичности. Заголовки уходят при каждом вызове инструментов этого сервера.

Список серверов в токене — **необязательное локальное сужение** гранта: пусто → монтируется всё, что шлюз разрешил
ключу. Идентификатор токена — внутреннее имя (из него
собирается ref ключа `MCP_ACCESS_<ID>_LITELLM_KEY` и запись в `stateFile`): оно собирается транслитом из названия,
дубликаты получают `-2`, `-3`; человек его не вводит. Формат состояния —
`{version: 2, activeToken, tokens[], hiddenTokens[]}`; файл прежнего формата (`{activeToken}`) читается как есть,
поэтому обновление плагина не требует миграции.

Сборка обязательна перед запуском: host отдаёт только готовый `lib/client.js` (формат
`window.__ModuleLoader__.load({id, factory})`, внешние модули — `react` и базовые примитивы DSH).
`client/index.cjs` — обычный CommonJS без JSX, поэтому сборка сводится к обёртке
(`scripts/build-client.mjs`), без tsdown и node_modules.

### Раздел «Промпты»

Экран умеет отдавать в сессию готовые предметные инструкции (промпты «сделай сам»). Во встроенный
набор входит одна — настройка браузерного MCP (chrome-devtools) с видимым Chrome; остальные
инструкции репозитория (Exa, n8n, QA-набор, перевод на RU LiteLLM) подключаются своим `promptsDir`
или добавляются в `INCLUDED` скрипта сборки. Список — вкладка «Промпты», три действия:

| кнопка | что делает | сколько занимает |
|---|---|---|
| «Отправить» | сообщение уходит в очередь активной сессии через `conversation.sendSession` — композер не участвует | ~0.25 с на 15 КБ |
| «В поле ввода» | `SessionInput.setDraft` кладёт текст в черновик, отправляет человек | 1–2 с (редактор перестраивает 15 КБ) |
| «Копировать» | текст в буфер обмена | мгновенно |

Активная сессия определяется тем же предикатом, что у `ui-workspace`: строка каталога с
`retainedBy.mainView > 0` (публичного «дай текущую сессию» в 0.2.1-rc.2 нет).

Откуда берутся файлы:

- по умолчанию — **встроенный набор пакета** (`prompts/` рядом с `index.js`), настраивать нечего;
- `promptsDir` в конфиге — свой каталог, если нужны другие/дополнительные инструкции.

Встроенные копии — не источник правды: их собирает `scripts/sync-prompts.mjs` из
`deploy/dsh-bootstrap/*.md` репозитория verme. Перед релизом плагина:

```sh
pnpm run sync:prompts   # пересобрать ./prompts из deploy/dsh-bootstrap
pnpm run check:prompts  # гейт: падает, если копии разошлись с источником
```

Хост отдаёт только текст (`GET /api/prompts`, `POST /api/prompts/item`), вставку делает клиент:
он работает с композером как с пользовательским вводом, поэтому состояние React обновляется, а
автоотправки нет — 20-килобайтная инструкция попадает в сессию только после нажатия «отправить».

### Деньги: сколько осталось

Деньги считает шлюз LiteLLM, плагин только показывает. Два места:

- **чип под композером** — `conversation.composer.dock`, рядом с индикатором контекста: `$4.52 /
  $10.00` и полоска расхода; по наведению — короткая сводка: остаток, израсходовано за окно, сброс,
  расход за сегодня одной суммой, группа. Как индикатор квоты в codex-плагине, только в доке
  композера. Всплывашка намеренно короткая: длинные значения обрезаются многоточием, панель
  ограничена `min(320px, 100vw-32px)` и `60vh`, `pointer-events:none`; всё, что не влезло
  (разбивка по моделям, lifetime ключа), живёт в карточке «Деньги», а не в подсказке. Данные тянет
  `GET /api/budget` раз в минуту (и не дёргает при скрытой вкладке);
- **карточка «Деньги» во вкладке «Доступ»** — дашборд: крупно остаток и полоса, справа
  израсходовано и процент; плитки «лимит / сброс окна / сегодня / за 7 дней / ключ за всё время /
  группа»; столбики расхода по семи дням (пустой день — серый столбик и «нет данных» в title),
  **клик по столбику** переключает таблицу на модели этого дня (последний столбик = «сегодня»);
  таблица моделей — короткое имя, полоска доли, сумма, первые 6 строк и кнопка
  «показать все (N)» / «свернуть» (сервер отдаёт до 24 моделей на день, счётчик общий; дневная
  строка /spend/logs несёт готовый models, поэтому разбивка есть за любой день недели).
  Явные подписи,
  чтобы не читать «$90 за всё время» как остаток.

| запрос | что даёт |
|---|---|
| `GET <gateway>/key/info` | `spend` ключа за всё время, `max_budget` ключа (часто `null` — лимита нет), `expires`, `blocked`, число моделей, владелец/назначение из `metadata` |
| `GET <gateway>/user/info` | лимит владельца: `max_budget` + окно `budget_duration` (у нас `7d`), `spend` в окне, `budget_reset_at`, `user_role` |
| `GET <gateway>/team/info?team_id=` | команда пользователя: `team_alias`, `metadata.adfs_group` (AD-группа), состав, `spend`/`max_budget` команды |
| `GET <gateway>/spend/logs?start_date=&end_date=` | дневная сводка расхода: сумма за день + разбивка по моделям |

Важно: лимит стоит **на пользователе** (`$10 / 7d`), а не на ключе и не на этом DSH — его делят
все ключи аккаунта, поэтому «осталось $5.48» это остаток на аккаунт, а не «на этот чат».
Lifetime-`spend` ключа (`$90`) лимитом не является и живёт в отдельной строке с подписью «за всё
время». Группу видно и в интерфейсе: у нас `ai_developer` — это и `team_alias`, и `adfs_group`
в метаданных команды (состав 3 человека, лимита у команды нет).

Полоса расхода: жёлтая с 70%, красная с 90%.

**Статистика не блокирует экран.** `GET /api/state` отдаёт только кеш бюджета (`budget` = `null`,
если для активного токена ещё не считали) и в шлюз не ходит: вкладка «Доступ» рисуется сразу, а
деньги приезжают отдельным `GET /api/budget`. Пока ответа нет, карточка показывает «Считаем
статистику шлюза — остальные настройки уже доступны», затем подменяется данными (кеш из состояния
используется как мгновенная заготовка, чтобы не мигать скелетоном). Ответы шлюза кешируются на
`budgetRefreshMs` (по умолчанию 60 000 мс), кешируется только успех; параллельные запросы делят
один поход в шлюз (single-flight), `/key/info`, `/user/info` и `/spend/logs` идут параллельно, а
общий дедлайн `budgetTimeoutMs` (по умолчанию 8 000 мс) отдаёт частичный ответ с `error` вместо
повисшей вкладки. Смена ключа токена сбрасывает кеш — суммы прошлого аккаунта не показываются.
Ошибка шлюза не валит экран — карточка предупреждает, чип просто не рисуется.

Чего эти числа не знают: расход в шлюзе обновляется с задержкой ~10 с; для моделей без тарифа в
конфиге шлюза сумма занижена (считается по ценам LiteLLM, а не по факту счёта провайдера); остаток
на счету OpenRouter/провайдера через ключ не виден — только «сколько разрешено и сколько уже
потрачено по мнению шлюза».

## Пространство credential-ref — жёсткое правило

Плагин пишет ТОЛЬКО ref-ы вида `MCP_ACCESS_*` (константа `OWN_REF_PREFIX`):

1. `llmSecretRef` и все `tokens[].keyRef` обязаны начинаться с `MCP_ACCESS_`;
   чужой ref (например общий `LITELLM_BENCH_DSHLAB`) — ошибка конфига, ключ не перезаписывается;
2. ключ провайдера (`llm-pi-ai.providers.<llmProvider>.apiKeyEnv`) должен указывать на тот же
   `llmSecretRef`, иначе плагин обновляет свой ref, а маршрут читает чужой;
3. прежнее значение своего ref снимается снимком при старте и восстанавливается байт-в-байт на dispose
   (вместе со снятием MCP-монтирований).

объект `agents` (а не массив) и массивы `restores`/`pendingRestores`. Прежняя сборка без этих полей
валит проверку сразу — иначе доказательство молча снимается с чужого кода на том же порту.

## Эксплуатация

### Health-check

```bash
curl -s http://127.0.0.1:3080/verme-gate/api/diag | jq '{phase, barrier, applyPending, activeToken,
  servers: [.servers[] | {name, status, error}], key: .models.keyState, retry, lastError, snapshotWarnings}'
```

Признаки нормы: `phase=ready`, `barrier=false`, `applyPending=0`, все ожидаемые серверы `mounted`,
`models.keyState=ok`, `retry.attempts=0`, `snapshotWarnings` пуст.

| статус сервера | что значит | что делать |
|---|---|---|
| `mounted` | инструменты выданы активному токену | — |
| `no-token` | header-режим: личный токен не задан | задать на странице или `POST <pagePath>/api/secret {server, value}` |
| `no-env` | шлюз не видит обязательных env-переменных сервера | `GET /v1/mcp/user-env-vars/status`; ввести значение в строке сервера (кнопка «Переменные»), `setup_url` — запасной путь через админку шлюза |
| `key-error` | ключ токена отклонён шлюзом (`models.keyHealthError`) | проверить ключ токена/его права |
| `token-rejected` | личное значение НЕ принято (проба → 401/403, в т.ч. `status_code: 401` внутри ответа): тулзы сервера запрещены всем агентам, `phase=degraded` | заменить значение (кнопка «Переменные» / «Заголовки»), затем «Проверить» или `POST <pagePath>/api/verify {server}` |
| `not-mounted` / `error` | ошибка подключения MCP (после `mountRetryAttempts` попыток) | `servers[].error`, журнал |
| `no-active-token` | токен не выбран: список серверов остаётся на экране с этой причиной | «Подключить» на вкладке «Доступ» |

### Живость личного значения (verifyTool)

«Значение задано» не значит «значение рабочее»: подменённый или устаревший ключ той же длины монтировал
сервер, отдавал полный список инструментов и давал 401 только в момент вызова агентом. Поэтому сервер
проверяется вызовом тулза-пробы: `verifyTool` из конфига, а если он не задан — первый `*whoami*` тулз
сервера (для PDM/Redmine это `redmine_whoami`, отдаёт логин). Режим не важен: header-режим проверяется
личным токеном, client-headers — сохранёнными заголовками, gateway — вызовом через шлюз (значение лежит
в его user env vars, плагин его не видит):

| статус (`servers[].tokenStatus`, `verify[]`) | что значит | что делает плагин |
|---|---|---|
| `token-ok` | проба ответила 200, из ответа взят логин (`login`/`email`) | сервер `mounted`, гейты по allowlist токена; в строке — «ключ принят» |
| `token-rejected` | MCP вернул 401/403 (в т.ч. внутри успешного HTTP: `status_code: 401`) | статус сервера `token-rejected` + причина, `phase=degraded`, **все** тулзы сервера запрещены агентам; на странице «токен НЕ принят» с причиной |
| `token-unknown` | пробы нет, таймаут, сеть или иной ответ MCP | сервер работает как раньше, но живость значения НЕ подтверждена (это не «всё хорошо») |

- проверка стартует после успешного монтирования (асинхронно, применение не задерживает), сразу после
  записи значения («Переменные» / «Заголовки» — без кеша) и по кнопке «Проверить» /
  `POST <pagePath>/api/verify {"server":"…"}` (без `server` — все серверы с пробой);
- результат кешируется по sha256 материала проверки (ключ, личный токен, заголовки, заполненность env) на `verifyTtlMs` (5 мин) — это и есть «бэкофф»:
  после рестарта проверка идёт один раз при монтировании, дальше MCP не дёргается чаще TTL; смена значения
  меняет отпечаток и инвалидирует кеш сама (снятие значения к тому же удаляет вердикт);
- статус сервера: при `token-ok` остаётся `mounted` (вердикт — в `servers[].tokenStatus`), при `token-rejected`
  статус сервера тоже становится `token-rejected`; `token-unknown` статус не меняет;
- запись значения — **точечное применение** (`applyServers`): перемонтируется только этот сервер, без общего
  барьера deny-all, без перемонтирования остальных серверов и без перетряхивания моделей; реестр, env-статус и
  живость ключа по-прежнему читаются (3 GET), но чужие монтирования и их статусы не трогаются;
- запись нового значения сбрасывает прежний вердикт и запрет тулзов: иначе новая запись унаследовала бы статус
  прошлой (само значение кеш не видит — видит только «заполнено / пусто»); сброс идёт **до** перемонтирования и
  поднимает «эпоху» сервера, поэтому проба, начатая до записи, при позднем ответе отбрасывается
  (журнал `verify <server> discarded: значение изменилось во время проверки`) — иначе просроченный 401 воскрешал
  запрет тулзов уже после смены значения;
- вердикт принадлежит значению и токену, а не серверу: смена активного токена (`/api/active`) очищает вердикты и
  запреты целиком, снятие значения или заголовка — для своего сервера; пробы «проверять нечего» (нет `verifyTool`,
  пустой header-режим, сервер не требует личных значений) снимают запрет, а не оставляют его навсегда;
- пока сервер не смонтирован, пробы нет: проверка ждёт монтирования (журнал `verify <server> deferred`),
  потому что проба — это тулз сервера; ручка `/api/verify` работает для любого сервера с пробой, включая
  gateway-режим (раньше отвечала 404 на синтезированные из реестра серверы);
- каждая проверка — строка журнала `verify <server> token-ok|token-rejected|token-unknown httpCode=… [id=…] [reason=…]`;
  значения токенов не печатаются нигде;
- ручка идемпотентна и не блокирует инстанс: при недоступном MCP ответ `token-unknown` приходит по
  таймауту `verifyTimeoutMs`, а `/api/state` продолжает отвечать (`scripts/lab/evidence-fix-verify-timeout.txt`).
### Авто-повтор обращения к шлюзу (R3)

- применение, упавшее из-за недоступности шлюза, даёт `phase=degraded` + `lastError`; инстанс продолжает работать;
- повторы: `retryDelaysMs` (по умолчанию `[1000,3000,9000]` с jitter ±15% ), дальше — фон каждые
  `retryBackgroundMs` (5 мин), пока состояние не станет `ready`; в журнале `retry #N через D мс (причина: …)`;
- `/api/diag` отдаёт `retry.{attempts,nextRetryAt,retryInMs,lastError}` — по `nextRetryAt` видно, когда ждать следующий повтор;
- повторяются не только применения токена, но и отдельные монтирования: `mountRetryAttempts` (3) попыток с
  задержкой 1.5/2.5 с, таймаут активации `mountTimeoutMs` (8 с), журнал `retry mount <server> через D мс (…)`;
  после исчерпания — `servers[].status=failed`, `phase=degraded`, `lastError`, и работают общие повторы ниже;
  статус монтирования пересчитывается и по `tools/change` (фибер может подключиться позже первой попытки);
- повтор **не снимает тулзы**: если упали отдельные серверы, перемонтируются только они (`retry <reason>:
  только упавшие серверы (…)`), полный проход с барьером остаётся для случая «реестр/ключ»; а когда
  применять нечего (нет токена, нет ключа, пустые гранты) ретраев нет вовсе — журнал пишет
  `retry off: применять нечего (…)`;
- `POST <pagePath>/api/refresh` — ручной повтор «сейчас»: сбрасывает таймер (счётчик начинается с `#1`);
- `keyHealthError` (ключ не подтвердился на `GET /v1/models`) и сбой статуса env дают `phase=degraded` и `lastError`,
  поэтому «зелёный экран при нуле смонтированных серверов» больше не возможен;
- во время применения доступ запрещён (барьер deny-all), поэтому неудачная попытка не расширяет гранты;
  после возврата шлюза состояние само переходит в `ready` — ручных действий не требуется.

### Снимок ключа провайдера (R2)

1. при старте плагин читает свой ref `llmSecretRef` и **один раз** сохраняет его значение в
   `<llmSecretRef>_SNAPSHOT` (credential-store, не файл состояния);
2. дальше снимок берётся из store — рестарт и `kill -9` его не теряют;
3. на dispose плагин возвращает значение ref-а байт-в-байт и **удаляет** снимок. Восстановление
   выполняется первым в cleanup, пока credential-store ещё жив; если сервис уже закрыт
   (`credentials-local is disposed`), плагин пишет ref аварийной атомарной записью в файл store
   (тот же приём, что и для своего же ref-а). Снимок удаляется только после подтверждённой записи;
   если запись невозможна (например, `chmod 500` на `DSH_HOME`), журнал пишет `status=pending`,
   ref не трогается, снимок остаётся — и следующий старт восстанавливает его **до** захвата ref
   (`pending-detected` → `status=ok source=startup-pending`). Статусы восстановлений видны как
   `restores`/`pendingRestores` в `/api/state` и `/api/diag`;
4. если снимка нет, а ref уже содержит ключ активного токена (плагин поставили на подменённый ref),
   плагин пишет `MCP_ACCESS_SNAPSHOT_UNKNOWN`, предупреждение в `snapshotWarnings` и в журнал —
   молчаливой подмены не происходит; если ref был пуст, пишется `MCP_ACCESS_SNAPSHOT_ABSENT`.

Проверить руками: `node scripts/lab/cred-store.mjs <DSH_HOME>/.credentials.yaml has <ref>_SNAPSHOT`
(печатает только наличие, длину и sha256).

### Агенты, жившие до старта плагина (R7)

Гейт нельзя навесить только на событие `agent/created`: при включении плагина на живом инстансе
(и при HMR-перезагрузке) агенты уже существуют. Поэтому плагин:

1. на старте перечисляет живых агентов через `ctx.get('agents').list()` и заводит им записи
   (`agent adopted … source=startup-enumeration`);
2. в каждом проходе гейта (`applyAgentGates`) сначала подбирает новых живых агентов
   (`adoptLiveAgents('apply')`), затем пересчитывает запреты от текущего состояния
   (`desiredDenied` → `reconcileGates`), а не инкрементит их — залипших запретов не остаётся;
3. `/api/diag` отдаёт `agents{candidates, gated, ungated, records, list[]}`; инвариант установки —
   `gated == candidates`, `ungated == []`, а в `agents.list[].visibleMcp` у каждого агента видно,
   какие MCP-тулзы ему реально доступны.

Проверено на агенте, созданном ДО старта плагина: при `token-rejected` вызов даёт
`Error: unknown tool` (до MCP не доходит, 401 от MCP нет), после возврата настоящего токена тот же
агент получает настоящий ответ (`scripts/lab/evidence-fix-r7.txt`).

### Ручная смена токена (R1)

`POST <pagePath>/api/active {"tokenId":"…"}` ставит применение в очередь: сначала барьер deny-all и снятие
монтирований, затем `activeToken` и его сохранение, затем подготовка/коммит грантов. В `/api/diag` во время
смены видно `barrier=true` и `phase=switching|starting`; комбинация «новый токен + старый allowlist» вне
барьера не наблюдаема (`scripts/lab/evidence-fix-r1.txt`: ~8000 сэмплов, 30 переключений, 0 нарушений).

### Про R4 (имена полей API)
